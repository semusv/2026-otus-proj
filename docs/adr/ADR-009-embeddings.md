# ADR-009: Эмбеддинги и реранкинг

- Статус: принято
- Дата: 2026-08-25
- Связанные: ADR-002 (VRAM-бюджет), ADR-003 (размерность коллекции)

## Контекст

Русскоязычные юридические тексты требуют мультиязычной эмбеддинг-модели. GPU (16GB) целиком
отдан под vLLM — эмбеддер и реранкер должны работать на CPU в процессе backend.
Модели скачиваются из HuggingFace при первом запуске (см. ADR-011 про зеркала).

## Решение

- **Эмбеддер: `BAAI/bge-m3`** (dense, dim=1024, контекст до 8192 токенов) — инференс на CPU
  внутри backend-процесса, батчевая обработка на ingestion.
- **Реранкер: `BAAI/bge-reranker-v2-m3`** (cross-encoder) — переранкинг топ-N fusion-результатов
  перед генерацией, только на query-пути.

## Trade-offs

| Критерий | bge-m3 | multilingual-e5-large | Инференс эмбеддера на GPU |
|----------|--------|----------------------|---------------------------|
| Русский язык | Сильно | Сильно | — |
| Длинные чанки (статьи актов) | До 8192 токенов без обрезки | 512 токенов | — |
| Dense+sparse одной моделью | Да (для будущего гибридного поиска) | Нет | — |
| VRAM | 0 (CPU) | 0 (CPU) | −1–2GB у LLM/KV-cache — отклонено |
| Latency rerank (CPU, top-20) | ~сотни мс — приемлемо | сопоставимо | быстрее, но дорого по VRAM |

e5-large отклонён: лимит 512 токентов режет статьи актов; bge-m3 покрывает длинные чанки
и оставляет задел под sparse/гибридный поиск. GPU-вариант отклонён: VRAM важнее для LLM.

## Последствия

- Положительные: единая размерность 1024 зафиксирована в схеме Qdrant; чанки до ~512–1024 токенов
  не обрезаются; реранкер заметно повышает точность цитат без доп. сервиса.
- Отрицательные / риски:
  - первый запуск тянет ~2–4GB весов с HF (нужен доступ или зеркало — ADR-011);
  - CPU-инференс ограничивает throughput ingestion — батчи и прогресс-логи обязательны;
  - модели пинятся по версии (reproducibility), кэшируются в volume.
