# Нагрузочный отчёт (этап 9)

> Дата прогонов: 26.08.2026 (ночная серия). Инструменты: locust 2.32.4 +
> micro-bench LLM-движка (`scripts/load_test/bench_llm.py`). Сырые результаты
> (CSV/HTML/docker-stats) — `scripts/load_test/results/` (вне git, воспроизводятся
> командами из конца файла).

## Резюме

| Профиль | Нагрузка | RPS | p50 | p95 | max | Ошибки |
|---|---|---|---|---|---|---|
| `GET /health` | 25 пользователей / 60 с | **220.7** | 5 мс | 11 мс | 350 мс | 0 из 13 056 |
| `POST /api/chat` non-stream, 1 польз. | 300 с | 0.107 (~7.4 с/ход) | 7.2 с | 7.6 с | 13.4 с | 0 из 31, 100% `ok` |
| `POST /api/chat` non-stream, 4 польз. | 180 с | **0.20** | 17 с | 20 с | 19.7 с | 0 из 35, 100% `ok` |
| LLM-движок напрямую, последовательно | 12 запросов | — | 0.98 с/запрос | 1.01 с | — | **258 ток./с** |
| LLM-движок напрямую, 4 параллельно | 8 запросов | — | 2.38 с | 2.69 с | — | **389 ток./с** агрегатно |

Ключевые выводы:

- На dev-стеке система держит **~220 RPS на лёгких эндпоинтах** и **~0.2 хода
  чата/с** на полном RAG-конвейере — без единой ошибки и деградации.
- Узкое место — **LLM-генерация**: ход чата = несколько LLM-вызовов конвейера
  (guardrails-классификатор, generate, evaluate) поверх CPU-rerank'а.
- LM Studio обслуживает запросы почти последовательно: параллелизм даёт лишь
  ×1.52 по токенам (258 → 389 ток./с). Целевой движок vLLM с continuous
  batching (ADR-001/002) снимет это ограничение.

## Методика

- **locust headless**, фиксированный `--run-time`, таймауты на каждом запросе
  (health 10 c, chat 170 c) — зависание исключено, после прогона машина свободна;
- профили разделены (`LOCUST_PROFILE=health|chat`): смешивать лёгкий эндпоинт и
  LLM-конвейер в одном прогоне бессмысленно;
- чат-профиль: логин один раз на пользователя, далее non-stream ходы
  (`stream=false`) с переиспользованием сессии; вопрос — конкретный по корпусу
  («Что регулирует ГПК РФ?»): расплывчатые формулировки уводят evaluate в
  re-plan loop (дизайн агента, этап 5) и размывают метрики latency;
- параллельно снимаются `docker stats --no-stream` (до/середина/после);
- tokens/sec — отдельный bench прямыми вызовами движка c подсчётом
  `usage.completion_tokens` (API чата бэкенда usage не отдаёт).

## Результаты

### 1. GET /health (25 пользователей, spawn 5/с, 60 с)

```
requests: 13056   failures: 0   RPS: 220.7
latency:  p50=5ms p90=9ms p95=11ms p99=16ms max=350ms
```

Путь Traefik → FastAPI без обращений к БД/моделям; max 350 мс — единичные
выбросы планировщика Windows/WSL2.

### 2. POST /api/chat non-stream, 1 пользователь (300 с)

```
turns: 31   failures: 0   статусы: 31 ok / 0 degraded
latency:  p50=7.2s  p95=7.6s  max=13.4s   throughput: 0.107 RPS
```

Установившийся режим полного конвейера: guardrail_in (LLM-классификатор) →
planner → retrieve_vec + expand_graph → fusion_rerank (CPU) → generate →
evaluate (LLM) → guardrail_out.

### 3. POST /api/chat non-stream, 4 пользователя (spawn 1/с, 180 с)

```
turns: 35   failures: 0   статусы: 35 ok / 0 degraded
latency:  p50=17s  p95=20s  max=19.7s   throughput: 0.20 RPS
```

При ×4 пользователей латентность растёт 7 → ~17 с (очередь движка), агрегатная
пропускная способность ×1.85. В первом прогоне этой конфигурации (бэкенд ДО
фиксов этапа 9) было 4 degraded из 28 — см. следующий раздел; после фиксов
деградаций нет.

### 4. Токены/сек LLM-движка (RTX 5070 Ti, qwen3.5-2b / LM Studio)

| Режим | Запросов | Латентность p50 | Токенов/ответ (средн.) | tok/s на запрос | Агрегатно |
|---|---|---|---|---|---|
| Последовательно | 12 (+прогрев) | 0.98 с | 242 | **258** | 256 |
| 4 параллельно | 8 | 2.38 с | ~240 | ~101 | **389** |

Генерация ~240 токенов занимает ~1 с: сам инференс быстрый, длительность хода
чата (~7 с) складывается из нескольких LLM-вызовов и CPU-фаз (эмбеддинг,
rerank). Параллелизм >4 на LM Studio прироста не даёт. Целевой стек
vLLM/Qwen3-8B-AWQ с continuous batching — предмет демо-прогона этапа 10/11.

### 5. Ресурсы контейнеров (docker stats, середина прогонов)

| Контейнер | health-профиль | chat ×4 |
|---|---|---|
| graphrag-backend | CPU 26%, RAM 1.27 GB | **CPU ~1300%**, RAM 1.81 GB |
| graphrag-qdrant | CPU 2.6%, RAM 372 MB | CPU 1%, RAM 376 MB |
| graphrag-neo4j | CPU 0.6%, RAM 843 MB | CPU 2.7%, RAM 845 MB |
| graphrag-postgres | CPU <1% | CPU <1% |

Backend при чат-нагрузке упирается в CPU: torch-фазы bge-m3/reranker
(CPU-device, ADR-009). RAM стабильна, утечек за серию прогонов нет.
Варианты разгрузки: `APP_RERANK_DEVICE=cuda`, уменьшение `APP_RAG_VECTOR_TOP_K`.

## Найденные и исправленные проблемы (результат этапа)

Нагрузка вскрыла дефект, невидимый на одиночных запросах:

1. **Отравление памяти диалога пустым ответом.** Ход с `degraded` и пустым
   `answer` (транзиентный сбой LM Studio «Error rendering prompt with jinja»)
   сохранял в PG пару user + assistant(""). Далее каждый следующий ход сессии
   получал assistant("") в истории → jinja-рендер шаблона модели падал («No user
   query found») → новая порция пустых ответов → сессия деградировала по кругу
   (в прогоне 1 польз.: 6 degraded из 7).
   **Фикс:** `save_turn` не сохраняет ход с пустым ответом; `load_history`
   фильтрует пустые сообщения (лечит и уже отравленные сессии).
2. **Переполнение контекста генерации.** Блок источников (top-5 × до 1800 симв.
   + граф-факты) на малых окнах модели приводил к обрезке промпта сервером и
   потере user-запроса — тот же jinja-сбой даже без истории.
   **Фикс:** `APP_GENERATE_CTX_CHAR_BUDGET=9000` — равномерная урезка текстов
   источников с сохранением маркеров [S#] (цитаты остаются валидными).
3. Попутно: нестабильный порядок user→assistant в истории при равных
   timestamp — явный сдвиг +1 мкс в `save_turn`.

После фиксов: последовательный профиль 31/31 ok, конкурентный 35/35 ok,
newman-gate ускорился с ~3 мин до 1 мин 13 с.

(CSV locust, report.html, docker-stats до/середина/после).

## Выводы

1. Функциональные и нагрузочные гейты этапа зелёные; система устойчива под
   нагрузкой (0 ошибок, деградации только по дизайну Agent Loop).
2. Для целевого профиля «десятки одновременных пользователей» критичен переход
   на vLLM (continuous batching) и GPU-rerank — архитектура готова,
   переключение конфигурацией (ADR-001/002, ADR-009).
3. SSE-стриминг (этап 5) снижает воспринимаемую латентность первого токена до
   долей секунд независимо от полной длительности хода.
